# Vibe Coding 全流程指南：如何从 0 到 1 学会 AI 辅助开发

> 这篇文章不是一篇单纯介绍 Codex、Cursor、Claude Code 等工具的“工具测评”，也不是鼓吹“不会写代码也能做软件”的宣传文。它更想回答一个问题：**一个已经具备计算机基础的人，应该如何系统学习 Vibe Coding，并把它真正变成自己的开发能力？**

---

## 1. 为什么要写这篇文章：不是介绍概念，而是讲清楚如何从 0 到 1 学会 Vibe Coding

我写这篇文章的初衷，不只是解释“什么是 Vibe Coding”，也不只是列举几个 AI 编程工具。更重要的是，我希望讲清楚：

> **一个程序员、计算机学生或科研开发者，应该如何从 0 到 1 学会 Vibe Coding。**

现在网上关于 Vibe Coding 的内容很多，大致可以分成几类：

1. **概念介绍类**：解释 Vibe Coding 是什么，强调自然语言生成代码；
2. **工具推荐类**：推荐 Cursor、Claude Code、Codex、Copilot、Windsurf 等工具；
3. **零基础造应用类**：强调不懂代码也可以用 AI 做网页、做小程序、做自动化脚本；
4. **最佳实践类**：强调上下文管理、代码审查、安全边界、测试和 Git；
5. **工程化方法类**：强调 AGENTS.md、Skills、MCP、自动化工作流和团队协作。

这些内容都有价值，但对于一个计算机专业学生或程序员来说，仅仅知道“AI 可以帮我写代码”是不够的。真正的问题是：

- 我应该先学什么？
- 我该如何开始第一个 Vibe Coding 项目？
- 我应该如何向 AI 描述需求？
- 我应该如何拆分任务？
- 我什么时候该让 AI 写代码，什么时候该让 AI 先做计划？
- 我如何判断 AI 写的代码是否可靠？
- 我如何避免 AI 把项目改乱？
- 我如何把一次性的 Prompt 沉淀成长期可复用的开发规则？
- 我如何用 Codex 这类 coding agent 做真实项目，而不是只做玩具 demo？
- 我如何把 Vibe Coding 用到全栈开发、科研复现、实验脚本、论文工程和个人项目中？

因此，这篇文章的核心目标是：

> **从学习路线、思维方式、工具链、工程规范和实践流程几个方面，系统讲清楚一个技术人员如何真正学会 Vibe Coding。**

我更愿意把 Vibe Coding 看成一种新的开发能力，而不是一个单独工具。

以前我们学习编程，往往是：

> 学语法 → 写小程序 → 学框架 → 做项目 → 调 bug → 学工程规范。

而现在学习 Vibe Coding，更像是：

> 学会描述需求 → 学会拆任务 → 学会管理上下文 → 学会指挥 AI 改代码 → 学会审查 diff → 学会运行测试 → 学会沉淀规则 → 学会构建自己的 AI 开发工作流。

这并不意味着传统编程能力不重要。恰恰相反，**越懂编程的人，越能把 Vibe Coding 用好。**

因为 AI 生成代码之后，最终仍然需要人来判断：

- 代码是否能运行；
- 架构是否合理；
- 业务逻辑是否正确；
- 是否存在安全问题；
- 是否破坏了已有模块；
- 是否真的满足需求；
- 是否值得合并到项目里。

所以，这篇文章并不是告诉你“如何逃避学习编程”，而是告诉你：

> **在 AI 编程时代，如何把原本的编程能力升级为 AI 协作开发能力。**

## 2. 什么是 Vibe Coding

### 2.1 一个适合程序员理解的定义

**Vibe Coding 是一种以自然语言为主要交互方式，由人负责目标、约束、判断和验收，由 AI 编程代理负责大量代码生成、修改、调试和文档工作的开发方式。**

它不是简单的“让 AI 写代码”，而是一次开发角色的变化：

- 过去：程序员主要是代码实现者；
- 现在：程序员逐渐变成目标定义者、任务拆解者、上下文管理者、代码审查者和工程负责人。

AI 可以帮你写 Controller、Service、Vue 组件、SQL、训练脚本、README、测试用例，但你需要决定：

- 为什么要写；
- 写在哪里；
- 和现有项目如何集成；
- 是否满足业务规则；
- 是否需要测试；
- 是否可以提交。

所以，Vibe Coding 的核心不是“放弃代码”，而是“把代码生产过程从手写为主，变成指挥、审查、迭代为主”。

### 2.2 两种 Vibe Coding：玩具式与工程式

网上对 Vibe Coding 有两种不同理解。

第一种是比较原始、比较“纯”的 Vibe Coding：

> 我直接告诉 AI 我想要什么，AI 生成代码，我不怎么看代码，只看运行效果，不行就继续让 AI 改。

这种方式非常适合：

- 周末玩具项目；
- 临时 demo；
- 一次性脚本；
- 快速验证想法；
- 不重要的个人工具。

它的优势是快，缺点也明显：代码质量不可控、难维护、安全风险高、项目一复杂就容易崩。

第二种是更适合程序员的工程式 Vibe Coding：

> AI 负责编码和执行，人负责架构、约束、审查、测试和最终责任。

这种方式适合：

- 长期维护的项目；
- 科研代码复现；
- 全栈应用开发；
- 团队协作项目；
- 需要上线或交付的系统；
- 需要持续迭代的个人项目。

本文主要讨论第二种，也就是：

> **负责任的 AI 辅助开发，而不是完全放手的“Accept All”式开发。**

### 2.3 Vibe Coding 与传统 AI 代码补全的区别

早期 AI 编程更多是代码补全：

- 补全一行；
- 补全一个函数；
- 根据注释生成代码；
- 在 IDE 中给出建议。

而 Vibe Coding 更强调项目级协作：

- 让 AI 阅读整个项目；
- 让 AI 理解目录结构；
- 让 AI 制定修改计划；
- 让 AI 修改多个文件；
- 让 AI 运行测试；
- 让 AI 根据报错继续修复；
- 让 AI 写文档；
- 让 AI 总结变更；
- 让 AI 根据 AGENTS.md 和 Skills 按规则工作。

因此，Vibe Coding 的关键不只是“模型会不会写代码”，而是：

> **你能否建立一套让 AI 稳定工作的开发流程。**

## 3. Vibe Coding 的核心变化：从 Coder 到 Commander

很多文章会把 Vibe Coding 总结成“从 Coder 到 Commander”。这句话很形象，但容易被误解。

它不是说程序员以后不需要懂代码，而是说：

> 程序员的工作重心正在从“亲自写每一行代码”，转向“设计任务、指挥 AI、检查结果、保证质量”。

传统开发中，你可能 80% 的时间都在写代码和查 API。

Vibe Coding 中，你更多时间会花在：

- 描述目标；
- 拆分任务；
- 管理上下文；
- 制定约束；
- 阅读 diff；
- 运行测试；
- 分析日志；
- 修正 AI 的方向；
- 沉淀开发规则。

这就像你从“一个人写代码”，变成了“带着一个很快但需要监督的初级工程师一起开发”。

这个“初级工程师”有几个特点：

- 写代码很快；
- 记忆大量框架和 API；
- 可以不知疲倦地改代码；
- 能读很多文件；
- 能解释报错；
- 但也会自信地犯错；
- 有时会过度修改；
- 有时会编造不存在的接口；
- 有时会忽略业务边界；
- 有时会为了修一个 bug 引入三个新 bug。

所以你不能完全放任它，而要学会管理它。

这正是 Vibe Coding 的核心能力：

> **不是让 AI 替你思考，而是让 AI 在你的约束下高效执行。**

## 4. Vibe Coding 面向的对象：为什么重点是程序员，而不是完全非技术人员

很多 Vibe Coding 教程会强调“零基础也能做应用”。这句话在某些场景下成立，比如做一个非常简单的静态网页、表单工具、个人小脚本或 demo。

但如果目标是做真实项目，尤其是长期维护的项目，那么 Vibe Coding 更适合以下人群：

### 4.1 程序员

程序员最适合使用 Vibe Coding，因为他们能看懂 AI 生成的代码，也能判断代码是否合理。

他们可以把 AI 用在：

- 快速生成模板代码；
- 快速理解陌生仓库；
- 快速调试报错；
- 快速写测试；
- 快速重构；
- 快速写文档；
- 快速完成重复性工程工作。

### 4.2 计算机专业学生

计算机学生可以用 Vibe Coding 加速学习：

- 学 Vue、React、Spring Boot、FastAPI；
- 做课程项目；
- 搭建个人网站；
- 写实验脚本；
- 复现论文代码；
- 理解开源项目；
- 做毕业设计或科研原型。

但学生尤其要注意：不要用 AI 代替基础学习。你可以让 AI 带你学，但不能让 AI 替你学。

### 4.3 科研开发者

科研人员使用 Vibe Coding 的价值非常大，尤其是在：

- 复现论文；
- 阅读陌生代码库；
- 修改数据集路径；
- 编写训练脚本；
- 批量跑实验；
- 分析训练日志；
- 画实验图表；
- 整理 reproduce.md；
- 快速验证一个想法。

科研场景中，AI 可以显著减少工程摩擦，但不能替代研究者对实验设置、指标、数据划分和结论的判断。

### 4.4 产品经理、设计师、非技术人员

非技术人员也可以使用 Vibe Coding 做原型，但他们更适合：

- 做低风险 demo；
- 做可视化原型；
- 做内部小工具；
- 做需求验证。

如果要做上线系统，仍然需要程序员参与审查和维护。

因此，本文的基本立场是：

> **Vibe Coding 可以降低编程门槛，但真正高质量的 Vibe Coding 仍然依赖技术判断力。**

## 5. 从 0 到 1 学习 Vibe Coding 的路线图

下面是我认为比较适合程序员和计算机学生的学习路线。

### 阶段 0：建立正确认知

目标：知道 Vibe Coding 能做什么，不能做什么。

你需要理解：

- AI 不是神；
- AI 会犯错；
- AI 生成的代码必须审查；
- AI 适合加速实现，不适合替你承担责任；
- 项目越复杂，越需要规则和流程；
- Vibe Coding 的质量取决于你的任务拆解能力。

这一阶段不要急着做大项目。你应该先建立基本原则：

1. 先计划，后编码；
2. 小步修改；
3. 每次看 diff；
4. 每次运行验证；
5. 重要项目必须用 Git；
6. 敏感信息不能交给 AI；
7. 不懂的代码不要直接合并。

### 阶段 1：学会用 AI 写小代码

目标：从简单任务开始，熟悉“自然语言 → 代码 → 运行 → 报错 → 修复”的循环。

可以练习：

- 写一个 Python 文件批量重命名图片；
- 写一个脚本统计 JSONL 文件行数；
- 写一个 Markdown 转表格工具；
- 写一个简单 Vue 计数器；
- 写一个 FastAPI hello world；
- 写一个读取 CSV 并画图的脚本。

这个阶段的重点不是项目复杂度，而是学会完整闭环：

> 提需求 → AI 生成 → 运行 → 报错 → 给日志 → 修复 → 再运行。

你要习惯把信息提供完整：

- 当前目录结构；
- 运行命令；
- 完整报错；
- 期望输出；
- 已经尝试过什么。

### 阶段 2：学会写好 Prompt

目标：从“随便问”变成“结构化指令”。

一个好的 Prompt 应该包括：

1. 背景：这个项目是什么；
2. 目标：这次要完成什么；
3. 约束：不能做什么；
4. 输入：文件、日志、接口、数据格式；
5. 输出：希望 AI 如何回答；
6. 验收：如何判断任务完成。

坏 Prompt：

```text
帮我修一下这个项目。
```

好 Prompt：

```text
我正在开发一个 Spring Boot 后端项目。现在用户登录接口返回 500。

请你先不要大范围重构，只根据下面的报错分析问题，给出最小修改方案。

要求：
1. 不修改数据库表结构；
2. 不修改接口路径；
3. 先说明原因，再修改代码；
4. 修改后给出 curl 测试命令。

运行命令：mvn spring-boot:run
报错日志：...
```

Prompt 不是越长越好，而是越清晰越好。

### 阶段 3：学会管理上下文

目标：让 AI 拥有足够信息，但不被无关信息干扰。

上下文包括：

- 项目目录；
- README；
- 配置文件；
- 相关源码；
- 报错日志；
- 数据结构；
- 接口文档；
- 业务规则；
- 之前的修改记录。

常见错误是：

- 给的信息太少，AI 只能猜；
- 给的信息太多，AI 抓不住重点；
- 对话太长，早期约束被遗忘；
- 项目规则散落在聊天记录中，没有沉淀成文件。

更好的做法是：

1. 让 AI 先阅读项目结构；
2. 每次只做一个功能；
3. 一个功能一个会话；
4. 重要规则写入 AGENTS.md；
5. 常用流程写成 Skill；
6. 复杂任务先让 AI 输出计划。

### 阶段 4：学会使用 Codex / CLI / IDE 插件

目标：从“聊天式问答”进入“项目级 AI 编程”。

普通 ChatGPT 问答适合：

- 学概念；
- 解释代码；
- 写小片段；
- 生成 Prompt；
- 帮你设计方案。

但真实项目中，你需要 AI 能够：

- 读文件；
- 改文件；
- 跑命令；
- 看 diff；
- 根据测试结果继续修复。

这时就需要 Codex CLI、IDE 插件或 App/Web 这类 coding agent。

推荐学习顺序：

1. 先在 IDE 插件里做局部修改；
2. 再用 CLI 在本地项目里完成中等任务；
3. 再用 App/Web 或云端 agent 做项目级任务；
4. 最后学习 AGENTS.md、Skills、MCP 等工程化能力。

### 阶段 5：学会审查 AI 代码

目标：不要只看结果能不能跑，而要看代码是否值得保留。

每次 AI 修改后，至少检查：

- 是否删除了不该删的文件；
- 是否修改了无关模块；
- 是否引入新依赖；
- 是否改变公共接口；
- 是否硬编码路径或密钥；
- 是否绕过异常处理；
- 是否破坏已有测试；
- 是否写了重复代码；
- 是否只是在“糊弄”通过报错。

建议每次都执行：

```bash
git diff
git status
```

对于后端项目，还要运行：

```bash
mvn test
```

对于前端项目，可以运行：

```bash
npm run lint
npm run build
```

对于 Python 科研项目，可以至少运行：

```bash
python script.py --help
python train.py --config xxx.yaml
```

如果项目暂时没有测试，也要让 AI 给出最小验证命令。

### 阶段 6：学会沉淀规则和流程

目标：让 AI 不只是一次性帮你，而是长期稳定地参与项目。

你应该沉淀：

- README.md：给人看的项目说明；
- AGENTS.md：给 AI agent 看的项目规则；
- docs/：详细设计文档；
- scripts/：常用运行脚本；
- tests/：测试用例；
- .env.example：环境变量模板；
- Skills：可复用的任务流程；
- prompts/：常用 Prompt 模板。

当你做到这一步，Vibe Coding 就不再是“灵感式对话”，而是变成了一个可复用、可维护、可扩展的工程系统。

## 6. 使用 Vibe Coding 的前提条件

### 6.1 最低技术基础

如果你想把 Vibe Coding 用好，建议至少具备：

- 会使用命令行；
- 会使用 Git；
- 能看懂基本代码；
- 能区分前端、后端、数据库；
- 能理解项目目录结构；
- 能阅读错误日志；
- 知道如何启动项目；
- 知道什么是依赖、配置、环境变量。

你不需要记住所有语法，但要能判断 AI 写的东西是否大致合理。

### 6.2 对全栈开发的基础理解

如果你要做全栈项目，需要理解：

- 前端负责页面和交互；
- 后端负责业务逻辑；
- 数据库负责持久化；
- 前后端通过 HTTP API 通信；
- 数据通常用 JSON 传输；
- 登录通常涉及 token、session、cookie；
- 实时通信可以用 WebSocket。

否则 AI 生成了前后端代码，你也很难判断字段是否对应、接口是否合理、鉴权是否安全。

### 6.3 对科研代码的基础理解

如果你要用 Vibe Coding 做科研，需要理解：

- 数据集格式；
- train / val / test；
- config；
- checkpoint；
- evaluation；
- metrics；
- seed；
- batch size；
- learning rate；
- log；
- baseline。

AI 可以帮你跑代码，但不能替你保证实验严谨性。

### 6.4 对风险的基本意识

你需要知道哪些操作危险：

- 删除文件；
- 清空数据库；
- 强制 reset；
- 大版本升级依赖；
- 自动迁移数据库；
- 上传密钥；
- 暴露用户数据；
- 在生产环境直接运行 AI 生成的命令。

Vibe Coding 越强，越需要边界。

## 7. Codex 在 Vibe Coding 中的使用方式

Codex 可以看作一个面向软件开发的 AI coding agent。它不只是聊天机器人，而是可以理解代码库、修改文件、运行命令、根据报错继续迭代的开发助手。

### 7.1 Codex App / Web

适合项目级任务，例如：

- 阅读 GitHub 仓库；
- 分析项目结构；
- 修复 issue；
- 生成 PR；
- 做代码审查；
- 处理较大的重构；
- 并行探索多个方案。

适合的 Prompt：

```text
请阅读这个仓库，先不要修改代码。请输出：
1. 项目目标；
2. 目录结构；
3. 核心入口；
4. 如何启动；
5. 如何测试；
6. 你建议我从哪里开始修改。
```

### 7.2 Codex CLI

CLI 适合本地开发，特别适合程序员日常使用。

适合：

- 在当前项目中修改代码；
- 运行测试；
- 修复报错；
- 生成脚本；
- 查看 diff；
- 逐步完成一个功能。

典型工作流：

```bash
cd your-project
git status
codex
```

然后在 Codex 中输入：

```text
请先阅读当前项目结构，并告诉我如何启动项目。不要修改文件。
```

确认它理解项目后，再让它做具体修改。

### 7.3 Codex IDE 插件

IDE 插件适合局部开发。

适合：

- 解释当前文件；
- 修改当前组件；
- 补全一个函数；
- 重构局部逻辑；
- 根据当前文件生成测试；
- 修改一个接口。

如果任务涉及多个文件、运行命令和测试，CLI 往往更合适。

### 7.4 Codex 的使用原则

无论使用 App、CLI 还是 IDE 插件，都建议遵循：

1. 先让它读项目，不要直接改；
2. 先让它出计划，再让它执行；
3. 一次只做一个功能；
4. 明确哪些文件不能动；
5. 修改后必须看 diff；
6. 修改后必须运行验证；
7. 大改动前先新建分支；
8. 不要把密钥交给它。

## 8. AGENTS.md：给 AI 编程代理看的项目说明书

### 8.1 AGENTS.md 是什么

AGENTS.md 可以理解为“写给 AI agent 的 README”。

README 是给人看的，AGENTS.md 是给 AI 看的。

它应该告诉 AI：

- 项目如何启动；
- 如何运行测试；
- 使用什么技术栈；
- 代码风格是什么；
- 哪些目录不能修改；
- 修改前要做什么；
- 修改后要如何验证；
- 哪些命令是危险的；
- 项目的业务规则是什么。

### 8.2 一个简洁的全局 AGENTS.md

```markdown
# AGENTS.md

## 基本原则
- 先理解项目，再修改代码。
- 修改前先说明计划，修改后总结变更。
- 优先做最小改动，不要无故重构大范围代码。
- 不要删除用户已有代码、数据、配置和文档，除非明确要求。
- 不要提交、上传或打印密钥、token、密码等敏感信息。

## 命令安全
- 可以运行只读命令，例如 ls、cat、grep、git diff、git status。
- 运行安装、删除、数据库迁移、批量格式化等命令前需要说明原因。
- 禁止执行 rm -rf、清空数据库、强制覆盖配置等高风险操作，除非用户明确确认。

## 代码要求
- 保持项目原有技术栈和代码风格。
- 新增功能要尽量补充必要注释和使用说明。
- 修改后优先运行相关测试或至少给出验证命令。

## 输出要求
- 每次任务结束后说明：修改了什么、如何验证、是否还有风险。
```

### 8.3 AGENTS.md 不宜太长

AGENTS.md 不是论文，不需要写得很长。

太长的问题是：

- AI 抓不住重点；
- 规则之间可能冲突；
- 后续维护困难；
- 占用上下文。

更好的写法是：

- 全局 AGENTS.md 写通用规则；
- 项目 AGENTS.md 写项目规则；
- 复杂流程写到 docs/ 或 Skills；
- AGENTS.md 中只放最重要的约束和索引。

## 9. Skills：把重复工作封装成可复用能力

### 9.1 Skill 是什么

Skill 可以理解为“给 AI agent 使用的专项工作流程”。

如果 AGENTS.md 是规则，那么 Skill 更像是流程。

例如：

- 代码审查 Skill；
- 科研复现 Skill；
- Spring Boot 接口开发 Skill；
- Vue 页面开发 Skill；
- Anomalib 实验 Skill；
- README 生成 Skill；
- 数据集适配 Skill；
- 训练日志分析 Skill。

一个 Skill 通常包括：

- SKILL.md：说明何时使用、怎么使用；
- scripts/：可执行脚本；
- references/：参考资料；
- assets/：模板或资源。

### 9.2 AGENTS.md 和 Skills 的区别

可以简单理解为：

> **AGENTS.md = 长期规则；Skills = 可复用流程。**

例如：

AGENTS.md 中写：

```markdown
- 修改代码前先说明计划。
- 不要删除 checkpoint。
- 修改后给出验证命令。
```

Skill 中写：

```markdown
当复现一个深度学习论文仓库时：
1. 先阅读 README；
2. 找训练入口；
3. 找配置文件；
4. 找数据集格式；
5. 给出最小运行命令；
6. 不要修改模型结构；
7. 跑通 baseline 后再改进。
```

### 9.3 什么时候应该写 Skill

当一个任务满足以下条件，就适合写 Skill：

- 你会反复做；
- 流程相对固定；
- 输出格式要求稳定；
- 容易因为 AI 自由发挥而跑偏；
- 你希望团队成员也按同一套流程使用 AI。

对于计算机研究生来说，很适合沉淀这些 Skills：

1. paper-reproduction：论文代码复现；
2. experiment-runner：批量实验运行；
3. log-analyzer：训练日志分析；
4. dataset-adapter：数据集格式适配；
5. fullstack-mvp：全栈 MVP 开发；
6. code-review：代码审查；
7. blog-writer：技术博客整理。

## 10. 高质量 Vibe Coding 的核心流程

一个稳定的 Vibe Coding 流程可以总结为：

> 需求澄清 → 技术选型 → 架构设计 → 任务拆分 → 让 AI 实现 → 运行验证 → 代码审查 → 文档沉淀 → 规则复用。

### 10.1 需求澄清

不要一上来就写代码。

先问：

- 我要做什么？
- 给谁用？
- MVP 包含什么？
- 什么暂时不做？
- 数据从哪里来？
- 如何判断完成？

Prompt：

```text
我想做一个【项目名称】。请你先不要写代码，而是帮我做需求澄清。

请输出：
1. 项目目标；
2. 目标用户；
3. MVP 功能；
4. 暂不实现的功能；
5. 技术难点；
6. 风险点；
7. 需要我确认的问题。
```

### 10.2 技术选型

不要盲目追求最新技术。

应该考虑：

- 我会不会用；
- AI 熟不熟；
- 文档多不多；
- 生态稳不稳；
- 项目复杂度是否匹配；
- 后续能不能维护。

对于个人项目，稳定比酷更重要。

### 10.3 架构设计

写代码前先设计结构。

Prompt：

```text
请基于当前需求设计项目结构。要求：
1. 不写具体代码；
2. 输出目录结构；
3. 说明每个目录作用；
4. 标明核心模块；
5. 给出开发顺序。
```

### 10.4 任务拆分

任务要拆小。

坏任务：

```text
帮我做完整项目。
```

好任务：

```text
请实现用户登录模块，只包括：DTO、Controller、Service、JWT 工具类和一个登录接口。不要修改房间模块。
```

### 10.5 实现与验证

每个任务完成后都要问：

- 修改了哪些文件？
- 如何运行？
- 如何测试？
- 有什么风险？
- 是否需要更新文档？

不要让 AI 写完就结束。

### 10.6 审查与沉淀

每次完成后做三件事：

1. 看 diff；
2. 跑测试；
3. 更新文档。

如果某个 Prompt 很好用，就保存到 prompts/。

如果某个流程会重复，就写成 Skill。

如果某条规则经常提醒，就写进 AGENTS.md。

```text

2. 只修改必要文件；

5. 启动命令；
6. 配置说明；

8. 后续开发计划。
```

## 13. 安全边界与常见风险

### 13.1 不要让 AI 随意执行危险命令

高风险命令包括：

```bash
rm -rf
sudo rm
DROP DATABASE
TRUNCATE TABLE
git reset --hard
git clean -fd
chmod -R 777
curl xxx | bash
```

这些命令不是永远不能用，而是不能在你没理解的情况下让 AI 自动执行。

### 13.2 不要泄露敏感信息

不要把以下内容直接交给 AI：

- API key；
- 数据库密码；
- 服务器私钥；
- 真实用户数据；
- 未脱敏日志；
- 公司内部代码；
- 论文匿名阶段不该公开的信息。

建议使用：

- .env；
- .env.example；
- 密钥占位符；
- 日志脱敏；
- gitignore；
- secret scanning。

### 13.3 不要无脑 Accept All

AI 生成的代码一定要审查。

尤其关注：

- 删除文件；
- 修改依赖；
- 修改数据库；
- 修改公共接口；
- 修改鉴权逻辑；
- 修改训练指标；
- 修改数据集划分。

### 13.4 必须使用 Git

Vibe Coding 必须配合 Git。

推荐流程：

```bash
git status
git checkout -b feature/xxx
# 使用 AI 修改
git diff
# 人工审查
git add .
git commit -m "feat: xxx"
```

如果 AI 把项目改坏了，Git 是你的安全绳。

## 15. 常见错误

### 错误 1：一上来就让 AI 写完整项目

解决：先需求分析，再架构设计，再分模块实现。

### 错误 2：只看效果，不看代码

解决：每次修改后都看 diff。

### 错误 3：不运行代码

解决：AI 写完不等于完成，能运行才算完成。

### 错误 4：报错信息给得太少

解决：提供完整命令、完整日志、环境信息、相关文件。

### 错误 5：没有项目规则

解决：写 AGENTS.md，把项目规则沉淀下来。

### 错误 6：上下文越来越乱

解决：一个功能一个会话；规则写文件；重复流程写 Skill。

### 错误 7：把科研结论交给 AI 判断

解决：AI 可以帮你整理实验，但实验设计和结论必须由研究者自己判断。

## 17. 总结

Vibe Coding 不是“不会编程的人让 AI 替自己写软件”，而是“懂技术的人用 AI 放大自己的工程能力”。

它真正重要的地方不在于某个工具，而在于一套新的开发方式：

> 人负责目标、约束、判断和验收；AI 负责生成、修改、调试和整理；项目通过规则、测试、文档和 Git 保持可控。

对于计算机学生和程序员来说，学习 Vibe Coding 的关键不是背 Prompt，而是建立一套能力：

1. 能描述清楚需求；
2. 能拆分复杂任务；
3. 能管理项目上下文；
4. 能让 AI 小步修改；
5. 能审查 AI 代码；
6. 能运行和调试；
7. 能沉淀规则；
8. 能把一次成功经验变成可复用流程。

如果你刚开始学习，可以从一个小项目开始：

- 先做一个简单脚本；
- 再做一个小前端页面；
- 再做一个简单后端接口；
- 再做一个完整 MVP；
- 再尝试复现一个科研模型；
- 最后把自己的流程沉淀成 AGENTS.md 和 Skills。

当你能做到这一点，Vibe Coding 就不再是“让 AI 帮我写点代码”，而是成为你自己的 AI 时代开发方法论。

真正的 Vibe Coding，不是放弃编程能力，而是把编程能力升级为：

> **需求表达能力 + 架构判断能力 + AI 协作能力 + 工程验收能力。**
